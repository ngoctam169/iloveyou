WebSocket hoạt động như thế nào trong hệ thống realtime?

Giải thích WebSocket handshake, connection lifecycle, heartbeat, reconnect, backpressure và cách scale hệ thống realtime qua nhiều server production.

Realtime Systems

Viết bởi Nguyễn Ngọc Tâm · 2026-09-28 · 13 phút đọc

WebSocket là giao thức cho phép client và server duy trì một kết nối hai chiều trên cùng một TCP connection. Sau khi handshake bằng HTTP Upgrade thành công, cả hai phía có thể chủ động gửi frame mà không cần client tạo request mới cho từng thông điệp. Đặc tính này phù hợp với chat, trạng thái online, dashboard trực tiếp và các luồng sự kiện cần độ trễ thấp.

Từ HTTP Upgrade đến kết nối hai chiều

Kết nối bắt đầu bằng một HTTP request chứa Upgrade: websocket và một khóa ngẫu nhiên. Server hợp lệ trả status 101 Switching Protocols. Từ đó, dữ liệu được đóng thành frame WebSocket thay vì HTTP response. TLS vẫn nên được dùng thông qua wss:// để bảo vệ dữ liệu trên đường truyền. Reverse proxy như Nginx cũng phải chuyển tiếp đúng Upgrade và Connection header.

WebSocket không tự định nghĩa message contract cho ứng dụng. Team vẫn cần quyết định envelope, event type, version, request ID, timestamp và cách biểu diễn lỗi. JSON dễ debug nhưng tốn băng thông hơn binary. Với phần lớn hệ thống nghiệp vụ, một envelope JSON rõ ràng thường đáng giá hơn việc tối ưu vài byte quá sớm.

Connection lifecycle quan trọng hơn thao tác send

Một demo có thể chỉ cần new WebSocket và onmessage. Production phải xử lý authentication, timeout, heartbeat, reconnect, resubscribe và duplicate event. Kết nối có thể mất khi điện thoại đổi Wi-Fi sang 4G, tab bị đưa vào background, proxy đóng idle connection hoặc server deploy. Mọi logic cần giả định disconnect là bình thường chứ không phải trường hợp hiếm.

Heartbeat ở tầng ứng dụng giúp phát hiện kết nối nửa mở mà TCP chưa báo lỗi. Server gửi ping hoặc event heartbeat định kỳ; client phản hồi hoặc cập nhật last-seen. Nếu quá ngưỡng, server đóng connection để giải phóng tài nguyên. Chu kỳ quá ngắn làm tăng traffic và CPU; quá dài khiến presence sai và tài nguyên treo lâu. Giá trị phù hợp phụ thuộc hạ tầng và yêu cầu sản phẩm.

Reconnect phải có backoff và jitter

Client reconnect ngay lập tức trong vòng lặp có thể tạo reconnect storm khi một cụm server vừa khởi động lại. Exponential backoff giới hạn tần suất thử, còn jitter làm các client không quay lại cùng một thời điểm. Sau reconnect, client cần lấy lại token nếu cần, subscribe lại channel và đồng bộ phần dữ liệu có thể đã bỏ lỡ.

Authentication không thay thế authorization

Trình duyệt không cho tùy ý đặt mọi header trong WebSocket constructor, nên hệ thống thường dùng cookie bảo mật, token ngắn hạn trong query chỉ khi rủi ro đã được cân nhắc, hoặc gửi message authenticate ngay sau khi kết nối. Token trong URL có thể xuất hiện trong log, vì vậy token một lần hoặc thời hạn rất ngắn an toàn hơn access token dài hạn. Dù handshake đã xác thực, server vẫn phải kiểm tra quyền khi subscribe channel và khi gửi command.

Không tin channel ID do client cung cấp. Mỗi subscription cần được đối chiếu với user, tenant và quyền hiện tại. Khi quyền bị thu hồi hoặc user đăng xuất, server nên có cách đóng connection hoặc hủy subscription. Rate limit cũng cần áp dụng cho message inbound; một kết nối dài không nên trở thành đường bỏ qua giới hạn của HTTP API.

Ordering, acknowledgment và duplicate

WebSocket giữ thứ tự frame trên một connection, nhưng ứng dụng phân tán vẫn có thể phát event không đúng thứ tự do nhiều producer, retry hoặc consumer song song. Nếu thứ tự quan trọng, event cần sequence theo aggregate hoặc conversation. Client có thể bỏ event cũ, phát hiện gap và yêu cầu đồng bộ lại. “Exactly once” thường rất tốn kém; thiết kế idempotent với event ID và at-least-once delivery thực tế hơn.

Đối với command quan trọng, client nên nhận acknowledgment chứa correlation ID và trạng thái. “Đã gửi lên socket” chỉ có nghĩa frame đã được đưa vào buffer, không chứng minh business action hoàn tất. Tách transport acknowledgment khỏi domain result giúp UI hiển thị đúng trạng thái pending, accepted hoặc failed.

Backpressure: khi client chậm hơn server

Một client mạng chậm có thể khiến send buffer tăng liên tục. Nếu server giữ mọi message trong RAM, vài kết nối chậm có thể gây thiếu bộ nhớ cho cả node. Hãy đặt giới hạn buffer, gộp các update có thể thay thế nhau, bỏ event không còn giá trị hoặc đóng connection khi vượt ngưỡng. Presence và typing indicator thường có thể drop; giao dịch nghiệp vụ thì cần lưu bền và đồng bộ lại qua API.

Nguyên tắc phân loại

Không phải event realtime nào cũng cần cùng mức đảm bảo. Phân loại theo “có thể bỏ”, “có thể đồng bộ lại” và “phải lưu bền” trước khi chọn buffer, retry và acknowledgment.

Scale WebSocket qua nhiều server

Khi có nhiều WebSocket node, user A có thể kết nối node 1 còn user B ở node 3. Node phải biết event nào gửi tới local connection và event nào cần phát qua backplane. Redis Pub/Sub phù hợp cho tín hiệu tạm thời; Redis Streams, Kafka hoặc message broker bền phù hợp hơn khi cần replay và consumer state. Sticky session có thể giảm churn nhưng không loại bỏ nhu cầu đồng bộ presence và routing.

Presence không nên chỉ là một boolean trong database. Một user có thể mở nhiều tab hoặc nhiều thiết bị. Mô hình nên theo dõi connection ID với TTL, rồi suy ra trạng thái user. Khi node chết đột ngột, TTL giúp record cũ tự hết hạn. Việc publish presence cho hàng triệu subscriber cũng cần coalescing để tránh fan-out không cần thiết.

Case mình từng gặp: transport đã realtime nhưng dữ liệu chưa chắc đã sẵn sàng

Khi làm realtime messaging, mình từng gặp kiểu lỗi mà nhìn riêng WebSocket thì connection vẫn ổn, event vẫn chạy, nhưng business state phía sau chưa kịp sẵn sàng. Hai request hoặc hai bước xử lý có thể tới gần như cùng lúc; bước sau kiểm tra database khi bước trước chưa insert xong nên hiểu nhầm là chưa có dữ liệu và tiếp tục xử lý.

Case như vậy làm mình đổi cách debug realtime. Mình không chỉ hỏi socket có connect hay message có gửi được không, mà phải ghép timestamp của request, log backend, trạng thái database và thứ tự event. Khi cần, mình thêm correlation ID để nhìn được cả một luồng thay vì từng log rời. Sau đó mới quyết định nên xử lý bằng transaction, lock, idempotency hay thay đổi thứ tự ghi và phát event.

Bài học từ case này

Realtime không làm mất race condition; nó thường làm race condition dễ xuất hiện hơn vì nhiều luồng xử lý xảy ra sát nhau. Transport và business consistency phải được quan sát cùng một timeline.

Quan sát hệ thống realtime

  • Số connection đang mở, connection mới và connection đóng theo nguyên nhân.
  • Handshake failure, authentication failure và subscription denial.
  • Inbound/outbound messages mỗi giây, kích thước frame và send-buffer depth.
  • Heartbeat timeout, reconnect rate và thời gian khôi phục subscription.
  • Event lag từ lúc tạo đến lúc client nhận, theo p95 và p99.
  • Memory trên mỗi connection và mức sử dụng file descriptor.

Khi không nên dùng WebSocket

Nếu client chỉ cần server đẩy dữ liệu một chiều và event không quá dày, Server-Sent Events đơn giản hơn, tự reconnect và đi qua HTTP infrastructure thuận lợi. Nếu dữ liệu cập nhật vài chục giây một lần, polling có cache có thể rẻ và dễ vận hành hơn. WebSocket tạo giá trị khi giao tiếp hai chiều, tần suất cao hoặc latency thấp thực sự quan trọng; nó không nên được chọn chỉ vì sản phẩm được gọi là realtime.

Thiết kế từ failure mode

WebSocket production là bài toán quản lý connection và trạng thái phân tán. Handshake chỉ là phần mở đầu. Authentication, authorization, heartbeat, backpressure, ordering, reconnect và observability mới quyết định hệ thống có ổn định hay không. Thiết kế tốt giả định mạng sẽ đứt, message có thể lặp và một node có thể biến mất; sau đó cung cấp con đường phục hồi rõ ràng cho client và operator.
